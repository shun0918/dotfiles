# Pull Request 作成

現在のブランチの差分をもとに Pull Request を作成する。

> **関連スキル**: `update-pr` と PR 本文のフォーマットを共有している。このファイルを修正する際は `update-pr/SKILL.md` も確認・修正すること。

## 引数

- `$ARGUMENTS`: 任意。関連する GitHub Issue の URL（例: `https://github.com/org/repo/issues/123`）

## 手順

### 1. 情報収集

以下を並列で実行:

- `git status`（未追跡ファイルの確認）
- `git diff` および `git diff --staged`（未コミットの変更確認）
- `git log main..HEAD --oneline`（ブランチ上の全コミット一覧）
- `git diff main...HEAD`（main からの全変更差分）
- 現在のブランチ名を取得

### 2. 関連 Issue の特定

以下のいずれかに該当する場合、PR 本文に関連 Issue を記載する:

- **引数に Issue URL が渡された場合**: その URL を使用
- **ブランチ名に `#数字` パターンが含まれる場合**（例: `feature/#123_add-login`）: リポジトリの Issue URL を組み立てる

該当する場合は `gh issue view <number>` でタイトルを取得し、`- <Issue URL>` の箇条書きで記載する（GitHub 上でタイトルが自動表示される）。

該当しない場合はこのセクション自体をスキップする。

### 3. PR 本文の作成

以下の構成で PR 本文を組み立てる。**日本語**で記述すること。

```
## 関連 Issue
（該当する場合のみ。箇条書きで Issue URL を列挙）

## ユーザーから見た変更
（エンドユーザーの視点で、UI や振る舞いがどう変わったかを説明する。
機能要件の変化と非機能要件の変化を分けて書く。
技術的な実装手段には触れず、「何ができるようになったか／どう変わったか」だけを書く。
変更がない側面はスキップしてよい）

### 機能
- 〇〇ができるようになった / 〇〇の挙動が△△に変わった

### 非機能
- パフォーマンス / アクセシビリティ / セキュリティなどの改善

## 実装詳細
（diff を読むだけではわからない背景情報を書く。
例: API 契約の変更、破壊的変更、マイグレーション手順、
採用したアプローチの理由や却下した代替案など。
diff を読めばわかるコード修正の羅列は書かない。
特筆すべきことがなければこのセクション自体をスキップ）

## テストケース
（この PR の挙動を手動で確認するためのチェックリスト）
- [ ] ケース1
- [ ] ケース2
```

### 4. 含めないもの

- コミットハッシュやコード片の引用（変更内容は diff を直接読めばわかる）
- 先頭の絵文字
- 無意味な連番（箇条書きの頭に 1. 2. 3. をつけない。`-` や `- [ ]` を使う）
- 過剰な修飾や装飾

### 5. PR 作成

- 未コミットの変更がある場合は、ユーザーに確認してからコミットする
- リモートにプッシュされていない場合は `git push -u origin <branch>` でプッシュ
- `gh pr create` で PR を作成する。HEREDOC で body を渡すこと
- PR タイトルは70文字以内で簡潔に
- 作成後、PR の URL をユーザーに返す
