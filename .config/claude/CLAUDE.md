# User について

- ユーザーは日本人。

# 開発スタイル

- コミットは branch を main からきって作業する
- コミット単位はその変更によって実装壊れないような単位でコミットする

# コードレビュー・実装について

- 既存の実装コードは間違っている可能性があります。常に疑問を持ってください。疑問を持った場合は、そのままにせずユーザーに対してフィードバックしてください。
- コードを書く前に、関連ファイルをすべて読むこと。盲目的に編集しない。
- 要件を完全に理解してから実装を始めること。
- エラーが出たら次に進む前に直すこと。失敗をスキップしない。
- ファイルを丸ごと書き直すより、既存ファイルの編集を優先する。
- 最もシンプルな解決策を選ぶ。過度な設計をしない。

# TDD について

- 自動テストを書く環境があるプロジェクトであれば、TDD で実装すること
- TDD は Kent Beck が提唱するやり方。すなわちテストリストを最初に洗い出し、一つずつテストがパスするように実装を進める
- テストは振る舞いを表すものにする。かつ、ドキュメントとして機能するように「〜の時〜であること」という形にする
- 検証するのは外から観察可能な振る舞いだけ。private な内部状態を直接覗くテストや、テスト都合で production の可視性を広げる行為 (test 用 getter を生やす / private を protected に格上げする / 「テスト用」ヘルパーメソッドを class に生やす) は反パターン
- 代替: 既存の public 契約 (callback / event / return value) 経由で観察する、テストダブルで呼び出し履歴・副作用を記録する、副作用のない純粋ロジックを別ファイルに切り出してそのまま test する

# Output

- 冒頭の挨拶や締めの言葉は不要。答えを最初の行に書く。
- 不確かなことは正直に「わかりません」と言う。推測で答えない。
- 簡潔に。情報を失わずに短く書く。

# ドキュメント・issue・PR のライティング

成果物テキスト (issue / PR / docs / 設計メモ) は以下の文体で書く。会話の応答スタイルとは別ルール。

- 箇条書き中心。必要最低限の情報のみ
- 体言止めで短く。1 項目 1 行を基本
- 敬語不要
- bold などの強調表現は使わない (構造化の見出し `##` は可)
- LLM 特有の冗長な前置き・修飾・締めを書かない
- 構造・経路・関係は文章で説明せず図 (mermaid 等) で示す
