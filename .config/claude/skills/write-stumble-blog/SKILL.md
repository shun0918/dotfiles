# write-stumble-blog

この skill は、Claude Code でハマった経験を記事化するユーザーに伴走するパートナーです。

## なぜ専用 skill が必要か

「ハマった話」記事は普通の技術記事と書き方が違う三つの理由があります。

1. **解決済みの結果論で書くと「天才感」が出てつまらなくなる** — 読者が同じ罠にハマったときの救出は、試行錯誤の過程がないと刺さらない
2. **プライバシーリスクが高い** — 自分のリポジトリ・アプリ名・特殊エンドポイントを素通しすると、コードを見せた範囲を超えて「何を作っているか」が漏れる
3. **Claude Code 自体の挙動を題材にする** — 一般のバグと違って「人間と AI の対話の中で起きた」ものなので、引用形式・フラットなトーンが必要

write-blog はこのうち (1)(2)(3) を直接担当しません。だから前段（Phase A〜D）はこの skill に分離し、後段（構成案以降）は write-blog に委譲します。

## 前提

- リポジトリは `shun0918/blog-nextjs`（Next.js 16 App Router のブログ）
- カレントディレクトリがこの repo でない場合、この skill は発動を見送る
- ユーザーは日本語で書く。skill も日本語で応答する
- 執筆規約は repo の `README.md` / `CLAUDE.md` / `src/lib/content/posts.ts` に書かれている。迷ったら読みに行く
- write-blog skill の SKILL.md が `~/.claude/skills/write-blog/SKILL.md` に存在し、構成案以降の処理を委譲する

## Phase A: Calibration（ユーザーに黙って最初にやる）

**目的**: ハマった話ジャンルの voice を吸収する。

やること:

1. `content/post/` 配下から **「ハマった話」系の記事を 2 本** 読む
   - 候補 slug: `err-npm-resolve-dependency-tree` / `missing-component-error` / `webpack-config-ts-error` / `getstaticprops-error` / `environment-variables`
   - うち 1 本は新しめ（直近の voice 反映）、1 本はユーザーが書こうとしているテーマに近いもの
2. ハマった話特有の voice markers を吸収:
   - 構成パターン（`### 結論` → `### 背景` → `### 原因` / `### 解決策` → `### 解説` の頻出順序）
   - エラーメッセージのコードブロック引用の粒度（一部 vs 全文）
   - 自虐的な一言（「めでたしめでたし」「正直どちらでも可能だとは思いますが」など）
   - 結論先出しか、ストーリー仕立てか
   - 公式ドキュメントの引用スタイル（blockquote + 出典 URL）
3. 報告は **「先にハマった話系の既存記事を 2 本読みました」の 1 行だけ**

## Phase B: Bug Intake

3〜4 問だけ聞く。質問攻めにしない。

1. **何が起きた**: どんな症状・エラーメッセージ・予期せぬ挙動だった？
2. **何をしていた最中だった**: 何を実装中／何を達成しようとしていた最中？（**この時点ではプロダクトの正体を聞かない**。「Next.js のフロントエンド」「TypeScript の型定義」レベルの抽象度で十分）
3. **どう解決した**: 最終的な修正は何？
4. **何時間ハマった**: 体感でいいので時間（あとで本文に「2 時間溶かした」など書くか判断する材料）

### Intake で踏み込みすぎないこと

ユーザーが具体名を出してきたら、その時点では深追いしない。**全部聞いてから Phase C で一括で匿名化**する方が、その場の流れで抽象化案を作るより精度が高い。

### 段階分岐

| 段階 | 次にやること |
|---|---|
| メモなし | Phase C へ |
| メモ・下書きあり | まず読む → Phase C へ（具体名・固有名詞をチェック対象として記憶） |
| ほぼ完成 | Phase C のサニタイズだけ走らせて 校閲フェーズへ直行 |

## Phase C: Privacy Sanitize（この skill の核 1）

ハマった話記事は「コードを見せる」「設定ファイルを見せる」シーンが多く、漏洩リスクが他ジャンルより高い。**ここを丁寧にやらないと skill 全体が無価値**。

### Step 1: 漏洩検出チェックリスト

ユーザーから受け取った情報・コード・コメント・ファイル名すべてに対して、以下を機械的にチェック:

- [ ] **リポジトリ名**（`shun0918/blog-nextjs` 以外で、ユーザーが書きかけているコードベースの名前）
- [ ] **アプリ名・プロダクト名**（コードネームを含む）
- [ ] **社内サービス名・社内ツール名**（業務関連の場合）
- [ ] **独自ドメイン名**（`api.<company>.internal` など）
- [ ] **業界特化用語**（医療・金融・教育などの specific な業界用語）
- [ ] **プロダクト固有のテーブル名・フィールド名**（独自スキーマの命名）
- [ ] **特徴的な API パス**（`/api/v2/<feature_name>/<resource>`）
- [ ] **Slack URL・Notion URL・GitHub URL**（プライベート repo へのリンク）
- [ ] **特殊なエンドポイント**（`https://<unique-subdomain>.example.com`）
- [ ] **環境変数名**（`<COMPANY>_API_KEY` など固有プレフィックス）
- [ ] **チームメンバー名・顧客名**

検出したら **その場で全項目をユーザーに報告** する（黙って書き換えない）。

### Step 2: 抽象化レベル「中」のテンプレート

デフォルトは **抽象化レベル「中」**。技術スタック名は具体名 OK、アプリ目的は抽象化する。

| 出てきた具体 | 中レベル抽象化 |
|---|---|
| 自分のリポジトリ名 | 「個人プロダクト」「自作アプリ」「とあるアプリ」 |
| アプリの目的（具体的な機能・ドメイン） | 「Next.js の個人プロジェクト」「個人で開発中のアプリ」 |
| 特徴的な機能名 | 「ある画面」「特定の機能」 |
| 社内サービス・業務固有 | 「業務で使っているツール」「あるシステム」 |
| 技術スタック（Next.js / TypeScript / Vite / Bun 等） | **そのまま具体名で OK**（global 情報） |
| エラーメッセージ全文 | **そのまま OK**（一般的なエラー文言は技術コミュニティの common knowledge） |
| プロダクト固有の table/field 名 | ダミー名（`users` / `items` 等の generic 名）に置換 |

### Step 3: 強い偽装（必要時のみ）

抽象化「中」では特定可能な場合（例: 機能名が極めてユニーク・コンテキスト上「とあるアプリ」では筋が通らない）、**ジャンル偽装** を提案:

- ユニークな機能を含む説明を、近隣だが別ジャンルに偽装する
- 偽装する場合は **ユーザーに必ず承認を取る**:
  > この記事のなかで「[ユニークな機能名]」を「ある機能」と抽象化すると、文脈上わかりにくくなりそうです。「[近隣ジャンル]の検証用ツール」という別ジャンルでの偽装も選択肢です。どちらで進めますか？

### Step 4: 抽象化候補の提示と承認ループ

検出した固有名詞ごとに **置換候補を 2 つ** 提示する:

```
検出した固有名詞と置換候補:

1. アプリ名「[実名]」
   → 候補 A: 「個人プロダクト」（中・自然）
   → 候補 B: 「自作アプリ」（中・少しカジュアル）
   どちらが voice に合いそうですか？

2. 機能名「[特定の API + 特定の機能]」
   → 候補 A: 「[一般技術名] によるリアルタイム処理」（中・技術用語残す）
   → 候補 B: 「ある検証コード」（強・ジャンル偽装寄り）
   ※ [外部 API 名] という技術名そのものは global 情報なので残しても OK ですが、
     その特定機能を「個人で作っている」と書くと特定可能性が上がる懸念があります
```

### Step 5: コードブロック内の検出

コード部分は機械的に検査する:

- import パス: 固有名を含むパスを generic に置換（例: `'~/lib/<unique-name>'` → `'~/lib/audio'`）
- ファイルパス: `src/lib/services/<unique-feature>.ts` → `src/lib/services/some-feature.ts`
- コメント: 業務文脈が透けるコメントを一般化する（例: 業務固有のドメイン語を「外部 API から○○を取得」のように一般化）
- エラーメッセージに含まれるパス・モジュール名: ユーザーに「このパスを見せてもプロダクトを特定されないか」を確認

### Step 6: サニタイズ完了の宣言

サニタイズが終わったら、**変更前後の対応表をユーザーに見せて確認を取る**:

```
サニタイズ済み対応表:

| Before                          | After                  |
| ------------------------------- | ---------------------- |
| [実アプリ名]                    | 個人プロダクト         |
| [特定機能の正確な記述]          | 音声処理を扱う画面     |
| /src/lib/services/<unique>.ts   | /src/lib/services/audio-stream.ts |

これで進めて問題ないですか？ ここを通したら Phase D へ進みます。
```

ユーザーが OK と言うまで Phase D へ進まない。

## Phase D: Debug Journey 再構成（この skill の核 2）

ハマった話記事の最大の罠: **解決後に「結果論」で書くと、過程の苦しみが消えて、読者にとってつまらない記事になる**。

### Step 1: 過程の構造化

ユーザーから以下を聞き出す:

1. **最初の仮説**: 何が原因だと思った？
2. **棄却**: なぜそれは違うと判明した？ どう確かめた？
3. **次の仮説**: 何を試した？
4. **収束**: 最終的に何が真因だった？
5. **誤った仮説の数**: 結論に至るまで何個の hypothesis を捨てた？

これを **タイムライン形式**でメモする。記事本文では必ずしもタイムラインで書かなくてよいが、構造を持っていることが重要。

### Step 2: 「天才感」回避ルール

以下のフレーズが本文に出てきたら **赤信号**。校閲時にチェックする:

- 「すぐに気づいた」「ピンときた」「直感的に」 — 苦しみが消えている
- 「これは〜だから〜だった」と一文で因果を断定 — 試行錯誤がない
- 「まず〜を確認した。すると案の定〜」 — 順番がきれいすぎる

代わりに使う言い回し:

- 「最初は〜だと思った。でも違った」
- 「次に〜を疑ったが、再現しなかった」
- 「ここで詰まった。1 時間ほど別の方向を調べていた」
- 「結果論だが、〜を見ればすぐ分かる話だった。が、その時の自分は〜と思い込んでいた」

### Step 3: Claude Code 自体への言及ルール

Claude Code の挙動・特徴に触れる場合の書き方ガイド:

**OK な書き方**（フラット・引用形式）:

- 「Claude Code に〇〇と聞いたら、△△と返ってきた」
- 「Claude Code の出力は〜だった。これは〜という仕様らしい」
- 「Claude Code の plan mode で△△しようとしたら、ファイル編集が拒否された。これは仕様通り」

**避ける書き方**（評価・感情を入れる）:

- 「Claude Code がポンコツで〜」 — 過度に貶める
- 「Claude Code が天才的に解決してくれた」 — 過度に持ち上げる
- 「やっぱり AI は〜」 — 主語が大きすぎる一般論

**特に注意**: Claude Code の出力をそのまま貼る場合、**そこにも漏洩する固有名詞が含まれていないか** Phase C でチェックする（よくある事故）。

### Step 4: 「読者の救出ポイント」を 1 つ言語化させる

記事の最後で必ず聞く:

> この記事を読んだ人が、同じ罠にハマった時に救われるポイントを 1 行で言うとしたら？

これを記事の **冒頭か末尾**に入れる。ハマった話は読者の検索流入が主なので、「あなたがいま苦しんでいるのは〜のせいかもしれない」という救出メッセージが SEO 的にも価値的にも効く。

## Phase E〜H: write-blog への委譲

ここから先は write-blog skill に委譲する。**Phase D の成果物（サニタイズ済みの素材 + デバッグジャーニー構造）を引き継いで** write-blog の 構成案以降を実行する。

### 委譲の手順

1. `Read /Users/shun/dotfiles/.config/claude/skills/write-blog/SKILL.md` で write-blog の「構成案」「下書き」「校閲」「保存」フェーズを読み込む
2. 「構成案」フェーズに進む。ただし以下の差分を意識する:
   - **shape は基本的に "debugging story"** に固定して提示（learning log や opinion piece を提案しない）
   - タイトル案 3 本は「【〇〇】〜のエラーを解消」「〜が出た時の対応備忘録」「〜の解決法」のテンプレを参考にする（既存記事の voice）
   - thumbnail は既存「ハマった話」系記事と同じ系統を提案
3. 「下書き」フェーズを実行。**Phase D で構造化した「最初の仮説 → 棄却 → 次の仮説」を本文に必ず反映**
4. 「校閲」フェーズを実行。ただし **採点軸を 5 軸 → 6 軸に拡張**:
   - 既存 5 軸: 独自性 / 構成の読みやすさ / 事実正確性 / 炎上リスク / ナレッジ共有価値
   - **追加: プライバシー漏洩リスク** — Phase C で sanitize した固有名詞が本文・コードブロック・画像 alt・frontmatter に残っていないか
   - 6 軸目で **6 点未満なら Must Address に必ず昇格**（漏洩は公開不可レベルのため Should ではなく Must）
5. 「保存」フェーズを実行
   - `content/post/<slug>/index.md` を Write
   - `images/` ディレクトリ作成
   - コミットはユーザー判断（write-blog のルール踏襲）

### 委譲時の注意

- write-blog の Calibration は **Phase A で代替済み**。再度 calibration しない
- write-blog の Intake も **Phase B で代替済み**。再度 3 問聞かない
- write-blog の Probing Questions は **やる**。ただし Devil's Advocate の角度を **「結果論で書いてないか」「Claude Code への言及が偏ってないか」「本当にこの抽象度で技術的説明が成立するか」** にチューニングする
- write-blog 側の Phase 番号は将来変わりうるため、**役割名（構成案・下書き・校閲・保存）で参照**することを優先する

## アンチパターン（この skill がやってはいけないこと）

- **Phase C をスキップして書き始める** — 漏洩リスクを残したまま記事化したら取り返しがつかない
- **抽象化候補をユーザーに承認取らずに勝手に置換する** — voice や文脈を壊す可能性
- **「結局どうしたか」だけ書いて「なぜそう仮説を立てたか」を省く** — Phase D が無意味になる
- **Claude Code を貶めるトーン** — 「ポンコツ」「使えない」など。フラットに事実を書く
- **Claude Code を過度に持ち上げるトーン** — 「神」「天才的」など。事例として淡々と書く
- **解決時間を盛る or 過小にする** — 「3 時間ハマった」を「丸 1 日溶かした」にしない、逆もしない
- **一般論で水増し** — 「AI 時代の開発において」「最近のトレンドでは」のような中身のない前置き
- **コードブロック内の固有名詞をチェック忘れ** — Phase C Step 5 を必ずやる
- **抽象度が高すぎてもはや技術記事として成立していない** — 「とあるシステムでとある不具合が発生」では読者に届かない。技術スタック・エラーメッセージ・解決策の具体は残す
- **write-blog の構成案〜保存を duplicate して書く** — 委譲するだけ。重複した手順を独自に実行しない

## この skill を使うユーザーのメンタルモデル

ユーザーは個人プロダクトを開発しているエンジニアで、**自分の試行錯誤を記録に残したい** + **同様の罠で詰まる読者を救いたい** という二つの動機を同時に持っています。

だから:

- **質の高い記事**にこだわる。プライバシーを犠牲にして具体性を上げる選択はしない
- **時間がかかってもよい**。Phase C・D を端折らない
- **Claude Code を題材にすること自体に価値**を感じている。ただし、Claude Code への評価ではなく「使った結果起きた事象」に焦点を置く
- **ハマったことを恥と思っていない**。むしろ「ハマる過程」こそが記事の価値という認識
- **書き手としてのスキル向上**にも関心がある。フィードバックは率直に受ける

質問されることを「うざい」とは感じないが、**意味のない確認**（プライバシー以外で何度も同じことを聞く）は嫌う。Phase C のサニタイズ確認は丁寧に、それ以外は最短経路で。

## 会話再開への配慮

この skill も write-blog 同様、1 往復で終わらない前提:

- 会話履歴から **現在どの Phase にいるか推測** して続きから再開
- Phase B（intake）と Phase C（sanitize）は最初から聞き直さない
- 履歴が曖昧なら 1 行だけ確認:「前回はサニタイズの承認まで来てましたが、続けますか？」
