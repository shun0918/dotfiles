# 開発の依頼を機能リードに渡す

依頼を、1機能＝1つの herdr ワークスペース（feat: 名前）に渡す。起動するのはリード（計画だけを書く、読み取り専用）まで。
実装は人間が `feature approve` を実行するまで始まらない。この skill は approve を実行しない。

## 守ること

- `feature approve` を実行しない。承認は人間だけが行う。
- GitHub・Slack・Notion に書き込まない。依頼の素材の取得は読み取りだけ。
- 依頼文は、人間に見せて確認が取れてから渡す。確認なしに `feature start` を実行しない。
- 依頼文のファイルは、対象リポジトリの外（`~/.dev-orchestrator/tmp/` など）に置く。リポジトリに入れない。

## 手順

1. **素材を集める**
   - 依頼が Slack・Notion・GitHub などのリンクなら、読み取りで内容と関連リンクを集める。足りない点は推測で埋めず、依頼文の「確認したいこと」に書く。

2. **依頼文（BRIEF）を書く**
   - 目的、受け入れ条件（何ができれば完了か）、制約・やらないこと、関連リンクの順に、短く書く。
   - 対象リポジトリのパスと機能名（小文字英数とハイフン、40 文字以内）の案を添えて、人間に見せ、直す点がないかを聞く。リポジトリが分からないときは、`~/.pr-reviews/config.json` の `local_repo_dirs` 配下の候補を挙げて選んでもらう。

3. **空きを確認する**
   - `~/.dev-orchestrator/bin/feature list` を実行する。計画中・実装中の機能が 2 件以上あるときは、人間に伝えて、先に進めてよいかを聞く。同じ名前・同じ依頼が既にあれば、新しく作らず `feature show <名前>` を案内する。

4. **渡す**
   - 依頼文を `~/.dev-orchestrator/tmp/<名前>.md` に書き、実行する:
     `~/.dev-orchestrator/bin/feature start <名前> --repo <リポジトリのパス> --task-file ~/.dev-orchestrator/tmp/<名前>.md`
   - worktree はリポジトリの規約の場所（`<repo>/.claude/worktrees`）に、無ければ既定の場所に作られる。
   - 失敗したら、メッセージをそのまま人間に伝えて止まる。

5. **人間に伝える**
   - herdr のワークスペース名（feat: 名前）と、lead タブで計画を作っていること。
   - 計画ができたら `feature show <名前>` で要点を読めること。PLAN.md の冒頭に「承認前にやること」（worktree 用の環境の起動など）があれば、先にそれを行う必要があること。
   - 計画に納得したら、人間が `feature approve <名前>` を実行すること。実行するまで実装は始まらない。

6. **計画ができたあと（人間に頼まれたとき）**
   - `feature show <名前>` と PLAN.md を読み、要点・確認したいこと・承認前にやることを短く報告する。承認の判断は人間に任せる。
