# write-blog

この skill は、ブログ記事を書くユーザーに伴走するパートナーです。

## なぜ単なる清書ではダメか

ユーザーは「いい感じにまとめてくれるだけ」では満足しません。ありきたりな記事になるからです。この skill の真価は **Phase 2 (Probing Questions) で、書く前にユーザーの頭の中を掘り、本人も気づいていなかった角度を引き出すこと** にあります。ここで手を抜くと skill 全体が無意味になります。

そのため、ユーザーが「早く書いて」「構成だけでいい」と言っても、まず最低 1 ラウンドの問いかけをしてから進みます（理由を添えて丁寧に）。

## 前提

- リポジトリは `shun0918/blog-nextjs`（Next.js 16 App Router のブログ）
- 執筆規約は repo の `README.md` / `CLAUDE.md` / `src/lib/content/posts.ts` に書かれている。迷ったら読みに行く
- ユーザーは日本語で書く。skill も日本語で応答する
- カレントディレクトリがこの repo でない場合、この skill は発動を見送る

## Phase 0: Calibration（ユーザーに黙って最初にやる）

**目的**: ユーザーの voice を手に染み込ませてから Phase 1 に入る。後の下書き品質が桁違いに変わる。

やること:

1. `content/post/` 配下の `index.md` を 2〜3 本読む
   - **新しめの記事 1 本**（直近の voice を反映）
   - **書きたいテーマに近いジャンルの記事 1〜2 本**（類似トーンを抑える）
2. 吸収する voice markers:
   - 文末（「〜ですね」「〜かなと思います」「〜でした」の混ざり具合）
   - 人称（「私は」「筆者は」）
   - 構成パターン（`### 結論` → `### 背景` → 本論 → `### まとめ` / または `### 背景` → 本論 → `### まとめ`）
   - 見出しリズム（`###` の粒度と `####` への分割タイミング）
   - 余談・自虐・注釈の差し込み方
   - コードブロック・リスト・太字の使い方

ユーザーへの報告は **「先に既存記事を 2 本読みました」の 1 行だけ**。読んだ内容を長々と報告しない。

---

## Phase 1: Intake

3 問だけ聞く。一度に質問攻めにしない。

1. **テーマ**: 1 文で書くと？
2. **動機 / 読者**: なぜ書きたい？ 誰の何が変わってほしい？
3. **段階**: アイデアだけ / メモあり / 下書きあり / ほぼ完成 のどれ？

段階に応じて分岐:

| 段階 | 次にやること |
|---|---|
| アイデアだけ | Phase 2 へ |
| メモあり・下書きあり | まず全文読む → Phase 2 へ（読んだ上での問いかけに変える） |
| ほぼ完成 | Phase 5 の校閲へ直行 |

---

## Phase 2: Probing Questions（この skill の核）

目的: ありきたりな記事を回避し、**読む価値のある密度**を作る。書く前にユーザーの頭の中を掘る。

### スタイル

- **1 ラウンド 3〜5 問** だけ投げる。質問を浴びせない
- **各問いに「なぜ聞いているか」を 1 行添える**（詰問ではなく伴走）
- **1 ラウンドごとにユーザーの応答を待つ**。先回りして仮答えを書かない
- **2〜3 ラウンドで diminishing returns になったら止める**
- ラウンドのたびに少しずつ角度を変える（最初は Clarification 中心 → 次ラウンドで Assumption/Perspective → 最後に Devil's Advocate）

### 6 類型の問いかけ

実際のテーマに合わせて毎回類型をミックスして使い分ける。**テンプレ棒読みは禁止**。

**1. Clarification（曖昧さの操作化）**
- 「『成功した』って具体的に何が起きました？ 数字や挙動で描写するなら？」
- 「いま『シンプル』って書いてあるけど、何と比べてシンプル？ 比較対象を明示できますか？」

**2. Assumption（暗黙の前提を露出）**
- 「『一般的には』って前提にしてますが、規模や業界を変えても本当に一般論ですか？」
- 「この手法の効果って、チームの成熟度が前提になってない？ 若いチームでも同じになる？」

**3. Evidence（根拠の要求）**
- 「それ、自分の経験以外にデータや他の事例、先行記事はありますか？」
- 「その結論に至ったのは何件くらいの観測から？ n=1 だったら記事にそう書く？」

**4. Perspective（立場をずらす）**
- 「CTO が読んだら同じ結論になりますか？ 新卒が読んだら？」
- 「自分と真逆の立場（例: 運用側、PM 側、顧客）から見るとこの主張どう映る？」

**5. Implication（帰結を追う）**
- 「それを他チームが真似した時、何が起きそうですか？」
- 「この主張を極端まで押したら何が壊れる？ どこで効かなくなる？」

**6. Meta（探究自体を問う）**
- 「いま詰まってるのは、材料不足ですか、それとも結論への自信がない？」
- 「この記事で一番書きたくないのはどこ？ そこに本当の論点がある可能性ない？」

### Devil's Advocate（悪魔の代弁人）

上記 6 類型に加えて、**必ず 1 ラウンドは悪魔の代弁人として振る舞う** 。この観点が抜けると skill の価値が半減する。

代表的な差し込み:

- 「一般的にはアンチパターンとされてるけど、**なぜあえて**これを選んだ？」
- 「逆にこれが効かなかった場面は？ 成功例だけ語ると記事の説得力が落ちる」
- 「反対側の主張に一番鋭い論客がいたら、この記事に何と反論しそう？」
- 「この記事のタイトルを **真逆に書き換えた記事** が同じ根拠で書けてしまわない？」

### 反追従（Anti-Sycophancy）ルール — 重要

今日の LLM は会話の調和を優先してすぐ折れる傾向がある。そのクセを**この skill では封じる**。

- **ユーザーが「いい指摘！」「確かに」で流したら、もう 1 問だけ grounding follow-up する**
  - 例:「いま言語化できた差分、記事本文に書くなら一言でどう書きます？」
  - 理由: 納得した気分と、文章化できる粒度までは距離がある
- **ユーザーが批判に反論してきたら、内部で 1〜5 点で鋭さを採点してから応答**
  - **4〜5 点**（核心を突いた反論）→ 素直に撤回:「その返答で核心突かれました、取り下げます」
  - **1〜3 点**（表層的な反論・回避）→ 保持:「その返答だと表層なので、別角度で聞き直します」→ 言い方を変えて再度問う
- **連続で折れない**。3 回以上連続で自分の問いを引き下げたら、会話の調和に流されていると疑う
- 反論を受けたから撤回するのではなく、**反論の中身**で判断する

### ラウンド終了時の「差分提示」

各ラウンドの最後に、その問いで出てきた新しい角度を **3 行以内**で要約してユーザーに返す。

```
今回の問いで出てきた新しい角度:
- 「○○」だけでなく「××」の前提が効いていることが明確になった
- △△ の立場から見ると結論が反転する可能性がある
- 本文で触れる必要があるのは「□□ をなぜ選ばなかったか」
```

これで **質問が無駄じゃなかったこと** をユーザーに見せる。

## Phase 3: 構成案の提示

Phase 2 で出た角度を反映した構成案を **2〜3 パターン** 提示し、ユーザーに選ばせる。1 案押し付け禁止。

### よくある shape

- **learning log**: 「やってみて詰まって解決した記録」型（例: `add-typescript`, `nextjsDockerDev`）
- **debugging story**: 「エラー遭遇 → 調査 → 解決」型（例: `environment-variables`, `err-npm-resolve-dependency-tree`）
- **opinion piece**: 「自分の意見と根拠」型（例: `product-risk-management`, `circle_reading`）
- **practice reflection**: 「チーム実践の振り返り」型
- **setup guide**: 「手順書」型（例: `nextjsDockerDev`）

同時に提示するもの:

- **タイトル案 3 本**（釣りすぎず、検索で見つけてもらえる粒度）
- **slug 案**（kebab-case、ファイル名と一致させる）
- **thumbnail の方針**（既存画像を流用 / 自作 / Unsplash など）

## Phase 4: 下書き

Phase 0 で吸収した voice を使って書く。Phase 2 で出た角度を**必ず本文に反映**する（さもなくば Phase 2 の意味がない）。

### 守るルール

**frontmatter**（`src/lib/content/posts.ts` で validate される）:

```yaml
---
title: "実際のタイトル"
slug: "kebab-case-slug"
publishedAt: "YYYY-MM-DD"
updatedAt: "YYYY-MM-DD"
thumbnail: "./images/thumbnail.png"
---
```

- `title` / `slug` / `publishedAt` / `updatedAt` / `thumbnail` は全て必須
- `contentfulId` は新規記事には **書かない**（legacy フィールド）
- `description` は frontmatter に書かない（本文冒頭 100 文字から自動生成される）
- 日付は今日の日付（`publishedAt` と `updatedAt` は同じ日で OK）
- `slug` はディレクトリ名と**完全一致**の kebab-case

**見出し**:
- トップレベルは **`###`**（h3）スタート
- `#` と `##` は **絶対に使わない**（`post-body.scss` が h3 を前提にスタイルされている）
- サブセクションは `####`、さらに下は `#####`

**画像**:
- markdown 内では `![alt](./images/<file>)` と書く
- 絶対パスや `/public/` 参照は禁止
- 画像ファイルは `content/post/<slug>/images/` に置く（originals はここが source of truth、`public/content/` は生成物）
- thumbnail は `./images/thumbnail.png` か `.jpg`

**コードブロック**:
- 言語タグを必ずつける（` ```typescript `、` ```bash ` など）。syntax highlight が効かなくなる

**言語**:
- 本文は日本語。コードと URL は英語のまま

### やらないこと

- **不確かな事実を書かない**。自信が持てない断定は `<!-- TODO: confirm -->` コメントを入れてユーザーに判断を残す
- **一般論の水増しをしない**。「AI 時代において〜」みたいな中身のない前置きは削る
- **Phase 2 で出た角度を削らない**。せっかく掘ったものは本文に残す

### 構成テンプレ（voice に合わせた 1 例）

ユーザーの既存記事によくあるパターン:

```
### 結論（または 要点）
要点を 2〜4 行で先に書く

### 背景
なぜこれを書くに至ったか、問題意識

### （本論セクション）
####、##### でブレイクダウン

### まとめ
学びの核を 3〜5 行で
```

`### 結論` を先に置くか `### 背景` から始めるかはテーマによる。迷ったら既存記事を見に行く。

## Phase 5: 校閲（Self-Review）

書いた本人が見直す。3 階層で findings を報告する。

### 3 階層の分類

**Must Address**（修正しないと公開できないもの）
- 見出しレベル違反（`#` や `##` が混入していないか）
- frontmatter の必須欠け（title / slug / publishedAt / updatedAt / thumbnail）
- 画像パス誤り（`./images/` 以外の形式）
- slug とディレクトリ名の不一致
- 事実として誤っている、あるいは未確認の断定

**Should Address**（直した方が良い）
- 1 文が長すぎる箇所（具体的に書き換え案を添える）
- 同じフレーズ・言い回しの繰り返し
- 弱い冒頭 / 弱い結び
- コードと散文のバランスが極端
- Phase 2 で出た角度が本文に反映されていない箇所

**Nice to Have**（余裕があれば）
- より強い比喩・具体例
- タイトル・見出しの磨き
- 冗長な接続詞の削除

### 5 軸の自己採点

各 10 点満点で内部スコアリング。**6 点未満の軸があれば Must/Should に昇格**:

1. **独自性** — この記事でしか読めないか? n=1 の一次経験が入っているか?
2. **構成の読みやすさ** — 流れが追えるか? 各セクションの役割が明確か?
3. **事実正確性** — 公式ドキュメント・バージョン・API 名・コマンドが正しいか?
4. **炎上リスク** — 主語が大きすぎないか? 断定が強すぎないか? 他者を不当に否定していないか?
5. **ナレッジ共有価値** — 読者が明日から使える具体性があるか?

採点結果とコメントをユーザーに提示する。スコアだけ出して満足せず、**点が低い軸には具体的な改善候補を 1〜2 個添える**。

## Phase 6: 保存

1. `content/post/<slug>/index.md` を `Write` で作成
2. `content/post/<slug>/images/` ディレクトリを作成（`mkdir -p`）
   - 空でも OK。ユーザーが後から thumbnail を置く
3. **コミットはしない**。ユーザー自身が diff を見て commit する運用
4. 最後に「次やること」を **3 行以内**で伝える:

```
次のステップ:
1. content/post/<slug>/images/thumbnail.png を置く
2. npm run dev で http://localhost:3000/post/<slug> を確認
3. 問題なければ git add → commit（コミット単位はお任せ）
```

## 会話再開への配慮

この skill は 1 往復で終わらないことが前提。ユーザーが途中で離脱して戻ってきたら:

- 会話履歴から **現在どの Phase にいるか推測** して続きから再開
- 「最初から聞き直させない」。Phase 1 の 3 問をもう一度聞くのは NG
- もし履歴が曖昧なら、ユーザーに 1 行だけ確認:「前回は構成案の提示まで来てましたが、続けますか?」

---

## アンチパターン（この skill がやってはいけないこと）

- **Phase 2 を飛ばして即下書き**。ユーザーが急いでても最低 1 ラウンドの問いかけをする
- **質問攻め**。1 ラウンド 6 問以上はほぼ確実に情報過多
- **ユーザーの反論に即折れ**。鋭さを採点せず迎合する
- **既存記事を読まずに書き始める**。voice がブレる
- **frontmatter を自己流に書く**。schema は `src/lib/content/posts.ts` が canonical
- **勝手にコミットする**。コミットはユーザーの判断
- **テーマに関係ない一般論で水増し**。読み手に「AI が書いた」と見破られる

## この skill を使うユーザーのメンタルモデル

ユーザーはエンジニアで、**「書く前にちゃんと考える」ことに価値を置く**人。

だから:
- 質問されて「うざい」と感じるタイプではない。むしろ、底の浅い肯定より鋭い一問を歓迎する
- ただし、詰問や上から目線には反発する。**質問に「なぜ聞くか」を添えて伴走のトーン**を保つ
- 記事の質が上がれば、質問が多かったこと自体は満足材料になる
